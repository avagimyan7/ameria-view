# ameria-view — дизайн

Дата: 2026-09-20
Статус: утверждён к реализации

## 1. Цель

Личное локальное приложение для разбора собственных транзакций по картам и счетам
Ameriabank: сколько пришло, сколько ушло, куда именно уходят деньги, укладываюсь ли
в бюджет, и поиск по конкретным операциям.

Пользователь один — владелец счетов. Приложение не публикуется, не хостится
и не работает с чужими данными.

## 2. Источник данных

### 2.1 Почему не API

Официального API Ameriabank для физических лиц не существует. Публичные API банка —
это мерчантский платёжный шлюз VPOS, а не доступ к собственным операциям. В Армении
обязательный open banking не введён: ЦБ обсуждает локализацию PSD2 и в июле 2025
вступил в GFIN, но рамочного регулирования нет. Агрегаторы (Plaid, Salt Edge)
армянские банки не покрывают.

Скрейпинг интернет-банка отвергнут: хрупко, противоречит правилам банка, риск
блокировки аккаунта.

### 2.2 Выбранный источник

Файл выгрузки **myAmeria History**:
`https://myameria.am/history` → кнопка **Filter** справа → задать даты →
секция **Actions** → кнопка **Excel**.

Один файл содержит операции по **всем** счетам и картам сразу.

### 2.3 Реальная структура файла (проверено на выгрузке за 22.07–20.09.2026, 254 операции)

- Расширение `.xls`, но фактический формат — **XLSX** (ZIP + OOXML, сигнатура `PK`).
- Шапка банка занимает 7 строк (логотип, контакты, заголовок `Պատմություն`, ФИО, период).
- Строка заголовков — 8-я, данные с 9-й.
- Заголовки на армянском, 11 колонок:

| Колонка | Заголовок | Поле |
|---|---|---|
| A | `Ամսաթիվ` | дата, формат `DD-MM-YYYY` |
| B | `Փաստ N` | номер документа |
| C | `ԳՏ` | тип операции |
| D | `Ելքագրվող հաշիվ` | счёт списания |
| E | `Շահառուի հաշիվ` | счёт зачисления |
| F | `Վճարող/Շահառու` | плательщик / получатель |
| G | `Մանրամասներ` | детали (мерчант) |
| H | `Կարգավիճակ` | статус |
| I | `Մեկնաբանություն` | комментарий |
| J | `Գումար` | сумма |
| K | `Արժույթ` | валюта |

### 2.4 Установленные факты и ограничения

1. **`Փաստ N` бесполезен как идентификатор.** В реальном файле он содержит одно и то же
   значение во всех 254 строках. В синтетической тестовой фикстуре стороннего проекта
   он заполнен — то есть на чужих данных дефект не воспроизводится.
2. **Поле `Մանրամասներ` обрезано примерно на 30 символах.** Названия мерчантов рвутся
   на середине слова: `Ք: AKG MORE THAN A PHARMACY LLC YE`. Обрезка необратима.
3. **К карточным покупкам приклеен номер транзакции**: `ASK 23 LLC YEREVAN AM 887772`.
   Из-за него 150 покупок дают 137 различных описаний. Это мешает категоризации,
   но помогает идентичности — см. 5.2.
4. **`Վճարող/Շահառու` иногда содержательнее деталей** (`«ԱՍԿ 23» ՍՊԸ` — 50 раз),
   но иногда это мусор (`Արմենիան Քարդ/փոխհաշվարկներ` — 63 раза, просто ArCa).
   Правила обязаны смотреть в оба поля.
5. **Банк сам проставляет тип операции** в колонке `ԳՏ` — это готовая бесплатная разметка:

   | Тип | Кол-во в выборке | Значение |
   |---|---|---|
   | `Քարտային գործարք` | 150 | покупка картой |
   | `Փոխանցում քարտին` | 25 | перевод на карту |
   | `Փոխանցման միջնորդավճար` | 22 | комиссия за перевод (отдельной строкой) |
   | `Իմ հաշիվների միջև` | 21 | перевод между своими счетами |
   | `Հաշվին փոխանցում` | 16 | перевод на счёт |
   | `Տոկոսի մարում` | 9 | погашение процентов |
   | `Վարկի մարում` | 8 | погашение тела кредита |
   | `Ավանդի համալրում` | 2 | пополнение депозита |
   | `Վարկի տրամադրում` | 1 | выдача кредита |

6. Все операции выборки — в AMD, статус `Հաստատված`.
7. Комиссии приходят **отдельными строками**, а не полем внутри операции.

## 3. Архитектурные решения

Локальное браузерное приложение, без бэкенда, без сети.

**Стек:** Vite + React 19 + Vitest (как в соседнем проекте `arvix`).

**Парсинг XLSX:** `fflate` (распаковка ZIP) + встроенный `DOMParser`, свой парсер
на ~150 строк. SheetJS отвергнут: около мегабайта кода ради файла, структура которого
известна точно. Компромисс принят осознанно — свой парсер требует собственных тестов,
зато не содержит непрозрачной логики в самом ответственном месте.

**Графики:** собственный SVG, без chart-библиотеки. Нужны столбики по месяцам,
горизонтальные бары и кольцо долей.

**Модули** — вся расчётная логика вынесена в чистые функции, побочные эффекты заперты
по краям:

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `parse/` | XLSX → строки таблицы; про банк не знает | — |
| `import/` | строки → транзакции: направление, свои счета | `parse` |
| `rules/` | нормализация текста, подбор категории | — |
| `stats/` | агрегаты по месяцам, категориям, мерчантам | — |
| `store/` | IndexedDB, дедупликация, настройки | `import` |
| `ui/` | экраны на React | все выше |

`parse`, `import`, `rules`, `stats` не обращаются ни к браузеру, ни к состоянию,
поэтому тестируются на фикстурах без окружения.

**Хранение разделено по ценности:**

- Транзакции — в IndexedDB, считаются расходным материалом: всегда перевыкачиваются
  из банка.
- Ручная работа (категории, правила, бюджеты, подтверждённые счета) — в `rules.json`
  рядом с кодом, под git.

## 4. Модель данных

```
Transaction {
  key          string   // составной идентификатор, см. 5.2
  date         string   // ISO YYYY-MM-DD
  opType       string   // ԳՏ, как в файле
  fromAccount  string
  toAccount    string
  counterparty string
  details      string   // сырое, с обрезкой банка
  comment      string
  status       string
  amount       number   // целое, в лумах (1 AMD = 100)
  currency     string
  direction    'expense' | 'income' | 'internal' | 'unresolved'
  categoryId   string | null
}
```

**Деньги только целыми числами.** `3000.0` → `300000` разбором строки, без `parseFloat`.
Плавающая точка в деньгах даёт необъяснимые расхождения в итогах, а сходимость сумм —
единственное, ради чего приложение существует.

## 5. Импорт

### 5.1 Определение своих счетов

Автоматический засев, затем подтверждение пользователем:

1. оба счёта из строк с типом `Իմ հաշիվների միջև` (банк сам пометил их как свои);
2. счета списания из строк `Քարտային գործարք`.

На реальных данных так определилось 4 счёта, после чего **не осталось ни одной
неклассифицированной строки** (214 расходов, 11 доходов, 29 внутренних переводов,
0 неопознанных).

Найденный список показывается при первом импорте для подтверждения и сохраняется
в `rules.json`.

**Направление:** оба счёта свои → `internal` (исключается из «пришло/ушло», видно
отдельной вкладкой); списание со своего → `expense`; зачисление на свой → `income`;
ни один счёт не опознан → `unresolved`, операция попадает в «требует внимания»
и **не угадывается молча**.

**Статус:** в статистику идёт только `Հաստատված`. Прочее сохраняется, показывается
отдельно и не раздувает расходы.

### 5.2 Дедупликация

Выгрузки должны грузиться внахлёст по датам.

Ключ собирается из всех содержательных полей: дата, тип операции, оба счёта,
контрагент, детали, комментарий, сумма, валюта. `Փաստ N` в ключ **не входит**
(см. 2.4.1). На реальных 254 строках это даёт 254 уникальных ключа, коллизий нет.

Здесь работает на пользу тот самый хвостовой номер транзакции, который мешает
категоризации: он делает каждую покупку уникальной. **Для идентичности строка
берётся сырой, для категорий — нормализованной.**

**Страховка от потери настоящих дублей:** одинаковые строки внутри одного файла
нумеруются по порядку (`#1`, `#2`), и при повторной загрузке пересекающегося периода
нумерация воспроизводится. Два одинаковых перевода одному человеку в один день —
две разные операции, и вторая не должна исчезать. В текущей выборке таких нет.

### 5.3 Отчёт об импорте

Период, добавлено новых, отброшено дублей, попало в «требует внимания».

## 6. Категоризация

### 6.1 Два уровня

1. **Текстовые правила** — по склейке `details + counterparty + comment`,
   сопоставление **подстрокой**, без учёта регистра. Правила упорядочены,
   срабатывает первое подходящее.
2. **Тип операции** как запасной вариант: комиссии, тело кредита, проценты,
   депозиты, выдача кредита — точно и бесплатно.

Сопоставление именно подстрокой, а не по нормализованному равенству: обрезка банка
необратима, но правило `TELCELL` находит и `TELCELL`, и `TELCELL TRANSPORT YEREVAN AM 93`.

### 6.2 Нормализация

Алгоритм, явно и полностью:

1. снять префикс `Ք: `;
2. отрезать хвостовую группу из **двух и более** цифр (`/\s+\d{2,}$/`) — это номер
   транзакции;
3. схлопнуть пробелы, привести к верхнему регистру.

Порог в две цифры выбран по замеру на реальных данных: 137 сырых описаний
схлопываются в 53 группы, и при этом ни одно название мерчанта не повреждается —
все отрезаемые хвосты оказались обрезанными номерами транзакций
(`TELCELL TRANSPORT YEREVAN AM 93`, `ROSTOFARM LLC ROSTOFARM LLC 051`).
Более осторожные пороги (3+, 4+) дают 66 и 71 группу, то есть хуже склеивают
одного и того же мерчанта. Города и коды стран не вырезаются: обрезка банка делает
их появление нерегулярным, а выигрыша это не даёт.

Остаточный риск: если банк обрежет строку ровно после двузначного числа в самом
названии (`Ք: ASK 23`), нормализация даст `ASK`. Это **безопасно по построению**,
потому что нормализация используется только для группировки мерчантов на экране
и для подсказки текста нового правила. Ни сопоставление (6.1, идёт по сырой строке
подстрокой), ни идентичность операции (5.2, тоже по сырой строке) от неё не зависят,
поэтому ошибка нормализации не может ни потерять транзакцию, ни исказить суммы.

Предел метода всё равно существует и починке не подлежит: `AKG MORE THAN A PHARMACY LLC YE`
оборвано банком на середине слова «YEREVAN». Именно поэтому правила сопоставляются
подстрокой, а не нормализованным равенством.

### 6.3 Создание правил из интерфейса

При ручной разметке операции приложение предлагает текст правила, выведенный из
нормализованного имени, и показывает «затронет ещё N операций на такую-то сумму».
Подтверждение создаёт правило, которое применяется ко всей истории задним числом.

### 6.4 Приоритет

Ручная пометка конкретной операции → текстовое правило → тип операции → «Без категории».

Ручная пометка всегда сильнее правила: иначе правило будет молча перетирать решение
пользователя.

### 6.5 Сужение правила

У правила есть необязательный фильтр по направлению и типу операции. Это не
умозрительно: `Անձնական փոխանցում` входящий и исходящий — разные по смыслу вещи.

### 6.6 Очередь «Без категории»

Сортировка по убыванию суммы. На реальных данных стартовый набор правил покрывает
150 из 225 операций (67%), но **неразобранные 33% содержат больше денег, чем
разобранные** — 4,18 млн против 2,35 млн AMD, потому что крупные движения это
переводы, которые банк не описывает. Из 75 неразобранных операций 36 — это
`Անձնական փոխանցում` (25) и `Հաշվի համալրում` (11). Разбор двух-трёх десятков верхних
строк закрывает основную массу денег; хвост разовых покупок можно не трогать.

### 6.7 Стартовый набор правил

Поставляется с приложением, собран и проверен на реальных данных: ASK 23 / ԱՍԿ 23,
OPTIM MARKET, YEREVAN CITY, AKG, ROSTOFARM, TELCELL, Yandex.Go, Yandex.Plus,
Apple.com, Figma, Profit Soft, Ucom, Team Telecom, IDRAM Utility, парковка,
плюс армянские ключи для комиссий (`ԳԱՆՁՈՒՄ`, `Commission`, `Միջն.`) и зарплаты
(`Աշխատավարձ`).

## 7. Бюджеты

Месячный лимит на категорию. На экране: потрачено против лимита, прогресс и прогноз
«при текущем темпе лимит будет превышен к такому-то числу». Считается на существующих
агрегатах, отдельной логики не требует.

## 8. Экраны

**Импорт.** Приём файла, отчёт об импорте. При первом запуске — подтверждение
найденных счетов.

**Обзор.** По месяцам: пришло, ушло, чистый результат, столбики динамики. Топ категорий
за выбранный месяц. Отдельными строками — сколько съели комиссии банка и сколько ушло
на кредиты с процентами.

**Категории.** Доли расходов, проваливание в список операций категории. Бюджеты.

**Транзакции.** Таблица с поиском по тексту и фильтрами: период, сумма от-до, категория,
счёт, тип операции, направление. Разметка операций и создание правил. Отдельная вкладка
«Между своими счетами».

**Настройки.** Счета, категории, порядок правил, экспорт и импорт `rules.json`.

## 9. Тестирование

Vitest, без браузера — вся логика в чистых модулях.

**Фикстура:** обезличенная копия реального файла. Структура сохраняется со всеми
странностями (шапка на 7 строк, армянские заголовки, обрезанные мерчанты, постоянный
`Փաստ N`), имена и суммы подменяются. Коммитится в репозиторий.

Приоритет покрытия — места, где ошибка стоит денег:

1. **Поиск строки заголовков по именам колонок**, а не по фиксированному номеру.
   Лишняя строка в шапке не должна сдвинуть разбор на соседнюю колонку и превратить
   номера счетов в суммы.
2. **Разбор сумм:** `3000.0` → `300000`, `9.0`, `999999999.99` — без потерь.
3. **Направление:** расход, доход, внутренний перевод и обязательно случай
   «ни один счёт не мой» → `unresolved`.
4. **Дедупликация:** повторная загрузка пересекающегося периода не плодит дубли
   и не теряет настоящие одинаковые операции.
5. **Правила:** приоритет ручной пометки над правилом, срабатывание подстроки
   на обрезанном тексте, фильтр по направлению.
6. **Инвариант сходимости:** сумма по категориям равна сумме расходов;
   «пришло минус ушло» равно чистому результату. Расхождение агрегатов
   с транзакциями роняет тест.

## 10. Границы v1

**Входит:** все пять экранов, включая бюджеты.

**Сознательно не входит:**

- **Мультивалютность.** Сейчас все операции в AMD, курсов файл не содержит. Валюта
  хранится у каждой операции, статистика считается по валютам раздельно, но
  переключатель не показывается, пока валюта одна.
- **Чтение push-уведомлений myAmeria.** У пользователя iPhone — там это технически
  невозможно.
- **Любая синхронизация**, облако, мобильное приложение.

Если потребуется ускорить выпуск, первое, что логично отложить, — бюджеты
(раздел 7): они не влияют ни на модель данных, ни на импорт.

## 11. Приватность

- Приложение **не делает ни одного сетевого запроса**. Проверяется вкладкой Network.
- Выгрузки банка (`*.xls`, `*.xlsx`, `*.csv`, `/data/`) в `.gitignore` с первого коммита.
- Финансовые данные не покидают машину: нет сервера, нет облака, нет авторизации.
